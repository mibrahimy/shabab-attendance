3 Dynamic Depth — the core constraint

From your caveats: the hierarchy is not fixed. A small city may be 1 level deep; an established city may add layers. Each city head defines their own structure. So levels can't be hardcoded — the shape of the tree becomes data.

flowchart LR subgraph A["Small / new city"] A1["City"] --> A2["Park"] --> A3["Murabbi"] --> A4["Students"] end subgraph B["Established city (Islamabad)"] B1["City"] --> B2["Division"] --> B3["Zone"] --> B4["Sector"] --> B5["Park"] --> B6["Park Admin"] --> B7["Murabbi"] --> B8["Students"] end style A fill:#f0fdf4,stroke:#22c55e style B fill:#eef2ff,stroke:#6366f1
Implication: the current schema models depth implicitly — City → Park → Member-tree with fixed place levels. The target needs a single self-referential node tree where each node carries a type, and the allowed types & nesting are configured per city. The good news: Member.parentId already proves the self-ref-tree pattern works here.

4 Conceptual Model — how to make both problems data-driven

Two ideas solve both hard problems: (a) one typed node tree for the org, configured per city; (b) a many-to-many between people and positions so one member can hold several roles.

5 Resolved Data Model SETTLED

The full table inventory. Two different "each"es matter here: no separate table per level (Zone/Sector/Park are rows in one typed OrgNode, so adding a level is data, not a migration), but separate tables per concept (structure · people · positions · assignments have different lifespans). Cross-city comparison is in scope, so per-city catalogs map to a shared canonical spine.

── Global catalog — shared across all cities, enables cross-city comparison ──
CanonicalNodeType  id, name, rank          ← Region/Division/Zone/Sector/Park…
CanonicalPosition  id, name                ← Zonal Lead/Park Admin/Murabbi/Student…
Program            id, name                ← Murabbi Training, Shabab Batch 4 (national)
Function           id, name                ← Sports / Tarbiya / Skills / Inventory

── Structure — ONE tree: (global root) → Country → City → Zone → Sector → Park → Class ──
NodeType   id, cityId?, name(local label), rank,
           canonicalTypeId → CanonicalNodeType   ← cityId null = global level (Country, City)
OrgNode    id, parentId, typeId → NodeType,
           cityId?, countryId?, path, depth, name, segment?
                                           ← Country & City ARE node types — NO separate City/Country table;
                                             cityId/countryId = denormalized ancestor keys (from path), both nullable
  deferred until needed: `dimension` (parallel functional trees) · `allowedParentTypeId` (nesting rules)

── People + positions — separate from structure ──
Person     id, cityId, cnic?(unique where set; required for account-holders = username), name, phone,
           segment(junior|senior), status(pending|active|rejected)  ← stable identity
Position   id, cityId?, name(local),
           canonicalPositionId → CanonicalPosition,
           functionId? → Function          ← null = cross-functional; cityId null = national title
Assignment id, cityId, personId, positionId,
           orgNodeId, startDate, endDate?  ← many per person = multi-position

── Permissions — manageable: global catalog + per-position grants ──
Permission         id, key, name           ← capability catalog (NO scope field —
                                             breadth = where the position is anchored)
                                            (mark_attendance, create_event, manage_team,
                                             edit_structure, manage_users, evaluate_*…)
PositionPermission positionId, permissionId ← editable grant = the "manage permissions" surface

── Activity — every row FKs to Person; all share one shape ──
Attendance   id, cityId, eventId, personId, status, markedById  ← v1 — BUILD NOW
Event        id, cityId, orgNodeId, rosterDepth=1, segment?, audiencePositionId?,
             programId?, functionId?, type, date, endDate?, status  ← v1 (roster = anchor + depth)
  ── future activity, SAME pattern (cityId · personId · function? · program? · date · payload) ──
Registration id, cityId, personId, programId…   ← flow ①
HabitLog     id, cityId, personId, date, habit…  ← flow ④
Progression  id, cityId, personId, programId, period… ← flow ⑤
Evaluation   id, cityId, subjectPersonId, evaluatorId, functionId?, rubric, period…
                                          ← murabbi & student evals = ONE entity (subject + evaluator)

── Auth — unchanged shape ──
User       id, personId, passwordHash, mustChangePassword, email?  ← login; username = person.cnic
Session    id, userId, …
Deliberate choices: segment is a column not a table (small national enum, always on Person so "all juniors" works whether or not a city splits structurally). Program is global not per-city (Murabbi Training / Shabab Batch are national → program comparison is free). User stays separate from Person (most shabab never get a login, so don't pay a User row per person) — but when a User exists it always links a Person. Login username = Person.cnic — nullable column with a unique index (unique where set; students may omit it, no login), required at account creation for account-holders. Replaces email; email now optional contact. Person.status drives the approval onboarding.
v1 scope = attendance only. Build Attendance + Event now. Every other activity type — Registration, Habits, Progression, Evaluation — is the same Person-centric shape, added when its flow ships; the core model doesn't grow to accommodate them. Evaluations (of murabbi & student) are one entity: a record with a subject person + an evaluator, function-scoped, gated by an evaluate_* permission. Murabbi-eval vs student-eval differ only by rubric + the subject's position — no structural change needed to support them.

How cross-city comparison works

Because each per-city NodeType / Position carries a canonical FK, comparison is just "group by the canonical id, optionally split by cityId." Each city keeps its own local label (one city's "Halqa" = another's "Park") but rolls up to a shared spine.

All Park Admins nationwideAssignment ⋈ Position WHERE canonicalPositionId = ParkAdmin
Junior attendance, every cityAttendance ⋈ Person WHERE segment = junior GROUP BY cityId
Compare Park-level attendance across citiesOrgNode ⋈ NodeType WHERE canonicalTypeId = Park GROUP BY cityId

How permissions resolve

Position implies permissions, and the grant is editable data — no deploy to change what a role can do. There is no scope field: breadth = how high the position is anchored in the tree.

active Assignment (Person holds Position at OrgNode N)
  × PositionPermission (that Position grants Permission X)
  → Person may do X on target T  iff
        T ∈ subtree(N)                       breadth = anchor height (path prefix)
    AND (position.functionId is null  OR  T.functionId = position.functionId)

  anchor at park → that park · at city → whole city · at country → whole country · at root → everything
One rule, no enum. Replaces User.roles + canManageTeam entirely. "Manage permissions" = editing PositionPermission rows. Broad-read + narrow-write = two assignments at different heights (read at city root, write at park). Super-admins = a position at the global root.

Cross-city POC / oversight SETTLED

Islamabad is the center: its members act as POCs overseeing other cities. This is oversight (a scope grant), not structural membership — so it's the same Assignment mechanism, pointed across city boundaries. Identity stays single-city; reach spans cities.

RuleResolution
Identity vs. reachPerson.cityId = home (Islamabad), single & unchanged. Assignment.cityId = the target node's city, so a person's assignments may span cities.
MechanismA "City POC" position assigned at each overseen city's root OrgNode. N cities = N assignments. Effective scope = union of home subtree ∪ each POC'd city. No DAG, no duplicated identity.
Access level ✦Read-only. POC position's PositionPermission set grants view_* only (analytics, team, attendance) — no write in overseen cities.
Visibility ✦Visible. POC is shown in the overseen city's Team/Users view as an external POC badge — attached at the city root, not a member in the chain (Person ≠ OrgNode, so no tree pollution).
Activity & scalingRead-only so no write attribution. POC queries scope as WHERE cityId IN (assigned set) — crosses tenants deliberately & explicitly; cityId-everywhere principle preserved.

✦ = decided this round.

Same mechanism, three anchor heights: country root → national/all-cities · specific city roots (N) → POC over exactly those cities · node inside a city → normal day-to-day role.

Functional domains — scope = structural × functional SETTLED

National titles ("Head of Sports") are bounded to their functional domain, not all activity at that level. So authority is a two-dimensional intersection: how far up the structural tree × which function.

authority of an Assignment =
    structural reach  (subtree of assignment.orgNode — breadth = anchor height)
  ∩ functional reach  (position.functionId, or ALL if null)

→ person may act on target T iff
    T is within structural reach
    AND (position is cross-functional  OR  T.functionId = position.functionId)
ExampleStructural × Functional
National Sports Headglobal × Sports → sports activity everywhere, not curriculum
Same person, also Park 3 MurabbiPark 3 subtree × null (cross-functional) → everything in their park
Zone Tarbiya Lead (future)Zone subtree × Tarbiya → tarbiya in that zone only
National Head of Inventoryglobal × Inventory → all assets everywhere (governs Asset, not attendance)
Functions: Sports · Tarbiya · Skills · Inventory. The first three are activity domains (govern Event/attendance); Inventory is an asset domain — it governs a future Asset/InventoryItem entity, not attendance. The structural × functional intersection is identical; only the governed entity type differs (so "governable entities carry functionId" generalizes beyond Events).

Now: Function catalog + Position.functionId + functionId on governable entities (Event; Attendance inherits it) + the intersection above. Plus nullable cityId on Position/NodeType so national titles live above any city.
Later (additive, no rework): real multi-level functional chains become parallel OrgNode trees keyed by the dimension field — each a clean single-parent tree, not a DAG. This retires the earlier "scope is purely structural" limitation for the functional axis.

Each functional hierarchy is independent, national-rooted & dynamic. A "National [Function] Admin" owns it and builds it freely — they may create city-wise heads or not; it is not bound to the geographic tree's shape. Superadmin creates a new dimension + provisions its National Admin (same cascade as City + City Admin, one level up). A city-wise function node may optionally reference the geographic city. UI: the same Hierarchy page with a dimension switcher (Geographic · Sports · Tarbiya · Skills · Inventory · + New).

Events & attendance — roster resolution SETTLED

An event is not tied to a fixed level. The creator picks an anchor node + a roster depth; the roster is computed live from the tree. People attach at the lowest structural node — Class/Halqa — so depth is coherent at every level (this replaces today's Member.classAssignment string).

Event roster spec:
  orgNodeId            anchor — ANY level: Class → Park → Zone → … → national
  rosterDepth = 1      levels below anchor to include; 2,3… widen; all = whole subtree
  segment?             jr / sr / null(both)
  audiencePositionId?  Student (class) · Murabbi (training); null = everyone assigned
  programId? functionId?  cohort / domain tags (used more as those flows mature)

resolve:
  roster nodes = OrgNode WHERE path LIKE anchor.path || '%'
                           AND depth <= anchor.depth + rosterDepth
  roster       = Persons with an ACTIVE Assignment at those nodes
                   AND (event.segment is null  OR person.segment = event.segment)
                   AND (event.audiencePosition is null  OR assignment matches it)
EventAnchor · depth · audience → roster
Murabbi's classClass · depth 0 · Student → that class's students
Park-wide classPark · depth 1 · Student → all classes' students in the park
Zone senior campZone · depth all · segment=senior → all senior shabab under the zone
Murabbi trainingCity · depth all · Murabbi → every murabbi in the city
Defaults & rules: depth defaults to 1 ("people directly under me"); the creator can widen. Who can mark = the single permission rule — mark_attendance over subtree(anchor) ∩ function; no separate role checks. Attendance = (eventId, personId) unique · status present/late/absent/excused · markedById.

Deferred: roster is implicit (live subtree query) for v1 → switches to explicit enrolled lists when Registration (flow ①) lands (better above park level). Recurring deferred — one Event per session for now (flag only).
Migration: current park events → anchor = the park's node, depth reproducing "whole park", audience = null → no behavior change.

6 Scalability Rules SETTLED

What keeps the model fast as it grows to N cities × years of attendance/habits/progression.

RuleWhy
Materialized path on OrgNodeSubtree scoping (permissions, analytics) becomes an indexed prefix scan path LIKE '/isb/z1/%' instead of a recursive CTE on every check. Reorg = one bounded UPDATE.
Denormalize cityId everywhereEvery queryable table carries it, so you never walk the tree to filter by tenant. Prerequisite for partitioning/sharding by city later.
Query by typeId, never raw depthCity A's depth-2 is a Zone; City B's (extra level above) is a Region. path/depth are for traversal; typeId is for meaning.
Temporal AssignmentstartDate + nullable endDate gives multi-position and history in one mechanism. Partial index on endDate IS NULL keeps "current holders" cheap.
Append-only activity + rollupsAttendance/habits/progression grow without bound. Keep rows immutable; serve dashboards from rollup tables/materialized views, not raw scans.
Config in reference tables, not JSONNodeType/Position are joined and filtered → real tables. Reserve JSON for truly open attributes you never query (e.g. a city's custom registration fields).

7 Design Decisions SETTLED

The forks that shaped the schema, and how each was resolved.

DecisionResolution
Person in the tree, or separate? Separate. OrgNode is a pure structural tree; people are Person rows attached via Assignment. A single-parent tree can't hold a multi-position person without duplicating identity — separation is what makes "one member, many positions" clean.
One table per level? No. Zone/Sector/Park/Division are rows in one typed OrgNode, distinguished by typeId. "Add a level above zone" is then data, not a per-city migration.
Per-city config strength Templated with a canonical spine. Each city defines its own ordered NodeTypes/Positions (local labels), but each maps to a shared CanonicalNodeType/CanonicalPosition — flexibility per city plus cross-city comparison.
Seniors / Juniors Always an attribute (Person.segment); structural division optional. Cities that split get a Division OrgNode too, but "all juniors" is always a segment query regardless — so it works whether or not a city separates them structurally.
Time / history Effective-dated from day one. Assignment carries startDate/endDate; activity tables (habits, progression) are append-only time-series. History and multi-position fall out of the same mechanism.
Cross-city comparison In scope. Canonical FKs on NodeType/Position + global Program + national segment enum let any metric group by canonical id and split by cityId.
Permissions Position implies permissions, and permissions are manageable. A Permission catalog (no scope field — breadth = anchor height) + an editable PositionPermission grant table. One rule: act on T iff T ∈ subtree(anchor) AND function matches. Fully replaces User.roles + canManageTeam.
Cross-city POC Read-only & visible. Oversight = a scope grant (a "City POC" position at the overseen city's root), not structural membership. Person.cityId = home; Assignment.cityId = target city, so assignments span cities. Shown as an external POC badge in the overseen city.
Functional scope & national titles Authority = structural × functional. National titles bound to their Function (Sports/Curriculum/…), not all activity at that level. Position.functionId + functionId on activity; cityId nullable so national titles live above any city. Future functional hierarchies = parallel OrgNode trees via the dimension field (not a DAG).
Events & roster Anchor node + configurable depth (default 1). Roster = Persons assigned within the depth band below the anchor, filtered by segment + target position. People attach at a Class/Halqa node (lowest structural level). Roster implicit for v1 (→ enrolled lists with Registration); recurring deferred.
All structural decisions are now settled. The remaining work is execution: a concrete Prisma schema, then a phased migration from the current City/Park/Member model to this one.
