1 The onboarding cascade — start to members

Each level creates the next. Only the first account is seeded outside the app; everything below is in-app.

flowchart LR SEED["① Seed (one-time)\nglobal root + first Superadmin"] --> SUP["② Superadmin\nadds Countries & Cities"] SUP --> CITY["③ City + its City Admin\n(provisioned together)"] CITY --> HIER["④ City Admin\nbuilds Hierarchy"] HIER --> MEM["⑤ Members added\nstaff (accounts) + students (profile-only)"]
Stage 0 — bootstrap: a one-time seed script creates the global root OrgNode + the first Superadmin (Person + User + Assignment @ global root; CNIC + initial password from env). The only account ever created outside the app.

2 Superadmin adds Countries & Cities — city + its admin together

Superadmin holds a global-root position. Creating a city also provisions that city's admin account inline — one separate account per city, no orphan cities. (More city admins can be added later.)

flowchart TD SA["Superadmin\n(Assignment @ global root, global perms)"] --> P1["Countries & Cities page"] P1 --> CC["Create Country\n→ OrgNode type=Country (under global root)"] P1 --> CY["Create City\n→ OrgNode type=City (under a Country)"] CY --> CA["Provision City Admin (inline)\nenter name + CNIC + phone →\nPerson + User + Assignment(City Admin @ city)"] CA --> TMP["Random temp password (superadmin shares)"] TMP --> READY["City ready — admin logs in (city-scoped),\nforced password change on first login"]

3 City admin defines the hierarchy — separate page

A dedicated Hierarchy page. The city admin builds their own tree (dynamic depth, per-city), optionally seeded from a template.

flowchart TD CADM["City Admin\n(Assignment @ city node, city perms)"] --> HP["Hierarchy page"] HP --> TPL{"Start from a template?"} TPL -->|yes| SEED["Seed levels: Zone → Sector → Park → Class\n(default NodeTypes)"] TPL -->|blank| DEF["Define NodeTypes (level names + order)\nper this city"] SEED & DEF --> BUILD["Build the tree:\nadd Zones · Sectors · Parks · Classes\n→ OrgNode rows; path + depth computed"] BUILD --> SAVE["Saved — city's structural tree exists"]
People attach at the lowest node (Class/Halqa). Levels are NodeType rows (data, not schema) — adding a level above Zone is just another node type.

4 Adding members — two paths

A member enters either by self-service (two public forms — Team registration or Shabab apply, both need approval) or by direct add (an admin/role-holder enters them — trusted, no approval). Staff get accounts; students are profile-only. Who can add is permission-driven, not only the city admin.

flowchart TD subgraph A["Path A — self-service (needs approval)"] PUB["PUBLIC registration form (no auth)\nname · CNIC* · phone · segment · requested city"] --> REQ["Person · status = pending"] REQ --> QUEUE["Approvals queue\ncity admin (that city) · superadmin (any)"] QUEUE --> REVA{"Approve?"} REVA -->|reject| REJ["status = rejected (notes)"] REVA -->|approve| PLACEA["Place Position @ node · status = active"] end subgraph B["Path B — direct add (no approval)"] ADDER["City admin / any role-holder\nwith add_member (within their subtree)"] --> KIND{"Staff or student?"} KIND -->|student| STU["Person + Assignment(Student @ Class)\nprofile only · bulk import OK"] KIND -->|staff| PLACEB["Person + Assignment(role @ node)\nstatus = active immediately"] end PLACEA --> ACCT["Staff → create User\nusername = CNIC · random temp password"] PLACEB --> ACCT ACCT --> LOGIN["Login → forced password change\n→ role's scoped permissions active"]
Who can add: add_member is scoped to one's subtree — the city admin is the broadest case, but a Park Admin can add murabbis/students in their own park if granted. Direct-add is trusted (the adder vouches) so staff accounts activate immediately; only the public form needs approval.
Students: profile-only, no account, no CNIC required, bulk-importable. Account policy (either path): username = CNIC · random temp password (≥12 chars, mixed) · bcrypt · forced change on first login.

Shabab application → interview → placement

The public surface is two forms: Team registration (staff → account) and Shabab apply (a youth/guardian → student profile). Shabab apply is profile-only, runs through approval into the park's unassigned pool, gets an interview stored on their profile, then a murabbi picks them into a class.

flowchart LR APPLY["PUBLIC apply form (no auth)\nname · phone/WhatsApp · segment · DOB · city + park · guardian\n☑ WhatsApp consent"] --> PEND["Person · status = pending"] PEND --> WA1>"WhatsApp template:\n"application received""] PEND --> AQ["Approvals queue (city)"] AQ --> REV{"Approve?"} REV -->|reject| RJ["status = rejected"] REV -->|approve| POOL["Student @ Park · unassigned pool\nstatus = active (profile only)"] POOL --> WA2>"WhatsApp template:\n"enrolled — murabbi will reach out""] POOL --> INT["Interview form filled\n(park admin / interviewer · conduct_interview)\nstored on profile"] INT --> SLOT["Murabbi / park admin\nassigns to a Class"] SLOT --> VIS["Assigned Murabbi can view the\ninterview on the student's profile"]
Two public routes: /register/team (CNIC required → account on approval) and /apply (shabab, CNIC optional → profile only). Both land in the same pending approvals pipeline; they differ only in form fields and whether a User is minted.
WhatsApp (Meta Cloud API): business-initiated messages must be pre-approved templates — fire on shabab submit (application_received) and on approval (enrollment_approved). Sent via a NotificationService → thin WhatsAppClient in server/integrations/ (never inline in a route); phone normalized to E.164, consent captured on the form.
Interview form: a structured questionnaire + free notes, stored as a FormResponse against the Person (history kept; latest canonical). Filled during intake by a holder of conduct_interview (subtree-scoped). Visibility follows the one rule: a role-holder sees it iff the student's Class assignment is in their subtree — so the assigned Murabbi sees it the moment the student is slotted into their class.
Forms are configurable — the city admin owns the questions. Interview and the 4-week Evaluation share ONE engine: a FormTemplate (per city · kind = interview | evaluation) holding ordered FormQuestions. Each question = a 1–5 score (MCQ) + a per-question comment box for the interviewer/murabbi's feedback. Filling one writes a FormResponse (person · evaluator · cycle) with a FormAnswer per question (score 1–5 + comment). The question text + scale are snapshotted onto each answer → editing/removing a question never rewrites past responses; the progress trend stays aligned by stable questionId. Overall = average of items (raw kept) + optional summary comment. City admin edits these on a Forms page.

5 Everyday attendance — mark your slice

The day-to-day loop for any role-holder, scoped by the one permission rule. On login the landing shows today's events — what needs marking now — not future ones.

flowchart LR LOGIN["Login (CNIC + password)"] --> DASH["Landing: TODAY's events\n(not future)"] DASH --> PICK["Pick event"] PICK --> SLICE["Roster = event roster ∩ MY scope\n(my slice)"] SLICE --> MARK["Mark — default ABSENT →\nflip present / late / excused"] MARK --> SAVE["Save (markedById = me)"] SAVE --> REP["Report: counts · rate · per-person"]
Landing = today. A Murabbi logs in to mark today's class, so the dashboard surfaces today's events. Future/past events live on the Events page (filter by date · function · status) — not the landing focus.

The slice mechanic

The roster you mark = the event roster ∩ your scope. Same event, different slice per marker; the event's attendance is the union. Falls straight out of "you can only mark people in your subtree."

Who logs in (a park-wide class event)Slice they mark
Murabbi of Class AClass A's students
Murabbi of Class BClass B's students
Park Admin (scope = whole park)all students — can fill gaps
A progress indicator ("X of Y slices marked") lets a higher role see which classes are done. No one steps on anyone else.
Marking UX: default everyone ABSENT (record who showed up); "mark all present" available; optional reason on excused/override (overrideReason); warn — not block — on completed/cancelled. Storage: on save, write an explicit Attendance row for every person in the slice, so "taken & all absent" ≠ "not taken yet". markedById = the marker.
Event creation (anyone with create_event, scoped): anchor (defaults to your node) · depth (default 1) · audience (segment + target position) · date/time · program/function. Park Admin → park-wide; Murabbi → their class.

Periodic — 4-week shabab evaluations & progress

Beyond daily marking, each Murabbi evaluates every shabab in their class on a 4-week cadence. The system surfaces an evaluation as due per student once 4 weeks have elapsed (from enrollment, then from the last evaluation) and lists it on the murabbi's dashboard next to today's events. Cycles accumulate into a progress view the murabbi and everyone above can read.

flowchart LR ENR["Shabab enrolled in class (t0)"] --> CYC["Every 4 weeks\n→ Evaluation DUE per student"] CYC --> DASH2["Murabbi dashboard:\n'N evaluations due'"] DASH2 --> FILL["Murabbi fills Evaluation\n(rubric scores + notes)"] FILL --> STORE["Stored on student profile\n(one row per cycle)"] STORE --> PROG["Progress view: score trend\n+ attendance trend over the course"] STORE --> CYC
Evaluation record per (student × cycle): a FormResponse (kind = evaluation) with evaluatorId = the murabbi, FormAnswers (1–5 score + comment per question), status: due → submitted, anchored cycle number + due date. Uses the SAME configurable FormTemplate engine as the interview (see Forms note above); one-time intake and recurring evaluation both hang off Person.
Who can see it (read up the tree): the assigned Murabbi and the whole hierarchy above (park → sector → zone → city admin) can view each shabab's evaluations and progress over the course — same subtree rule pointed upward, breadth = how high you sit (view_evaluation). The progress view is a per-student timeline: rubric scores across the 4-week cycles plus the attendance trend for the same course.
Open decision — what "4 weeks" counts: calendar weeks from enrollment (simplest, recommended; cycle length configurable per city/program) vs. 4 weeks of held classes (attendance-driven, more accurate but heavier). Defaulting to calendar-anchored unless you want session-counted.
